# ORION audit, night of 2026-11-17 to 18

What was compared: the backend in `C:\Users\lando\orion` (every module, the bridge, the tests, seven days of
telemetry in `data/turns.sqlite`) against the UI repo at commit fc3545a (`js/app.js`, `js/leo-client.js`,
`js/admin.js`, `js/business.js`, `js/tools.js`, `index.html`, `sw.js`, the docs). Numbers come from the running
system, not from reading code. Items are ordered by how much they matter; each says who owns the fix.

## 1. Built in the backend, not shown in the UI

1. **Opening line.** `snapshot.opening` and the `opening` event (the "while you were away" summary) are live, but
   `welcome()` in `js/app.js` still writes the fixed "Evening, Commander" greeting and `js/leo-client.js` has no
   `case 'opening'`. Filed in SYNC.md. *UI.*
2. **Background jobs and workflows have no home on the Tasks page.** Always = watch list, Daily = `routine_*`,
   Scheduled = anything with `due`/`next`. A job (`job_<id>`, source Jobs, added tonight) or a workflow (`wf_<run>`)
   shows only in the "now" strip while running; its result is a banner and an activity line, and once the banner is
   gone there is no place to read it. Add a "Background" list under the tabs (queued, running, done with `detail`).
   *UI.*
3. **Banner targets.** `notify.target.panel` is ignored: tapping any banner opens the Tasks drawer. Job and routine
   results say `panel: "activity"`; the natural landing is ORION's detail panel ("Recent work"). *UI.*
4. **Email verification state after a reload.** `email_alerts.pending: true` is sent while a code is out, but the UI
   keeps that only in memory (`ui.em.pending`), so a reload mid-verification shows "Send code" again and a second
   code is requested; the backend allows 3 codes an hour, so a third try locks the person out for an hour. Open the
   dialog on the code step when `pending` is true. *UI.*
5. **Admin data unused.** `admin_snapshot.telemetry_7d` and `admin_snapshot.email_alerts` arrive and are not drawn
   (`admin.js` renders `telemetry` for today only). Low priority. *UI.*
6. **No surface at all** for: people cards (`person_card`, `people_list`), lists and to-dos (`list_*`), saved
   workflows (`workflow_list`), the memory inbox (the banner says "N facts waiting for your review" and there is
   nowhere to review them; the HTTP API has `GET /memory/inbox`), phone push setup, per-account spend history. All
   reachable in chat or the CLI; a UI is optional. *UI, later.*
7. **"Always allow" for approvals.** Orion's `confirm` event carries `can_remember` and the Guard keeps approval
   rules, but the socket `approval` frame drops the flag and the UI has only Approve / Reject. A small protocol
   addition (`approve {id, remember: "1h"|"always"}`). *Both.*

## 2. Expected by the UI, not provided by the backend (or dead UI code)

1. **Stored password.** After a name + password login the UI saves `{url, name, password}` in plain text in
   `localStorage` (`save()` in `js/leo-client.js`) so the next visit logs in silently. Anyone with the phone or a
   shared PC profile can read the password. Fix: the backend answers a password login with a per-device token in the
   `snapshot` (revocable from the admin page) and the UI stores that instead. This is the most important item on the
   list. *Both.*
2. **The auto `brief` request cost money.** The UI sends `brief {}` six seconds after every connect when no brief
   is cached. For the owner that command used to make the morning brief if today's did not exist: one Haiku call per
   early-morning connect, with no gesture from the owner. Fixed tonight: the command returns today's report when it
   exists, else the free local summary, and never makes a brief (ACCOUNTS.md updated). *Backend, done.*
3. **Voice.** The UI transcribes with the browser's SpeechRecognition hard-coded to `en-US`; Kokoro on the PC is
   unused by the UI and `speaks` is false. French voice input cannot work even though Orion answers in French. Phase 2
   (server audio) is undesigned on both sides; at minimum pick the recognition language from the account. *Both.*
4. **Dead handlers.** The UI handles `tools` and `audio` frames the backend never sends; harmless.
5. **Business page.** Sample data with a note until Shopify is connected, as designed; `metrics` is omitted.

## 3. Correctness and safety

1. **Fixed tonight: the sonnet email Orion said it sent.** The pending send was correct; "yes send it" was not a
   strict yes, so it was treated as a new request, the pending action expired, the local brain called `email_send`
   again (pending again) and then wrote "sent" for a NOT DONE YET result; the next message expired that one too.
   Nothing was ever sent. Fixes: `is_yes(text, pending=True)` accepts a yes followed by the same action and refuses
   change requests; when a turn ends with an action waiting, code replaces any reply that claims "done" or does not
   ask yes/no with "Not done yet, Commander. Waiting for your OK to ... Say yes to proceed or no to cancel."
   Live-checked.
2. **No end-to-end test of `_chat` with a fake model.** The phantom email lived on a `_chat` path no test exercises;
   the suites cover the fast path, the Guard, tools, bridge frames and the cloud path, but not the decider → tool →
   speaker loop with a scripted model. A fake Ollama stream (one JSON generator) would make such tests cheap. *Backend.*
3. **Jobs hold the model lock.** A queued job's turn takes `Orion.lock`; a message typed meanwhile waits until the
   job's turn ends (local p90 is 20 s, Haiku 17 s). Acceptable for one person, but a job should also check that no
   device sent a frame in the last minute before it starts, as push does. *Backend.*
4. **Startup warnings.** `orion_server.py` uses FastAPI's deprecated `@app.on_event("startup"/"shutdown")`; move to a
   lifespan handler before a FastAPI upgrade removes it (two deprecation warnings in `data/logs/orion.err.log`).
5. **Transient network errors in connectors.** `_execute` retries httpx timeouts once; `imaplib` socket errors are
   not retried (one `getaddrinfo failed` in `routines.log` at 17:31 ended that email_triage run). *Backend, minor.*
6. **Daily tab sort.** `js/app.js` sorts routines by `next % 864e5`, which is UTC time of day; a 20:00 local routine
   sorts before 07:00 in Michigan. Sort by local hour and minute. *UI, minor.*
7. **Pictures from another device.** In shared-chat mode the echoed `images` are names, and `addUserMessage` reads
   `p.url` (undefined). Only matters with `server.ui_shared_chat: true`. *UI, minor.*
8. **What is right.** Origin check, 4401 lockout, PBKDF2 passwords, HMAC email codes, guest isolation enforced in
   `_exec_call` (guest risk forced to READ, tool list filtered), the audit log, taint gating after outside content,
   the untrusted wrappers; in the UI consistent escaping before `innerHTML`, blob downloads, reduced-motion paths.

## 4. Speed (seven days, 361 turns, owner 333)

| Path | Turns | First word, median | p90 | Notes |
|---|---|---|---|---|
| fast path (code) | 64 | 0.0 s | 0.0 s | time, maths, timers, lists, quick info, task hints |
| confirmation | 46 | 2.1 s | 3.2 s | the yes/no path |
| local brain | 215 | 8.5 s | 19.2 s | 112 used tools; the slowest 8 turns are all `remember` at 23 to 25 s |
| Claude Haiku | 35 | 11.9 s | 16.9 s | $0.10 in total |
| Claude Sonnet | 1 | 9.9 s | | $0.08 |

1. **The embedding model evicts the 9B.** Measured tonight: after one `/api/embed` call Ollama shows only
   `nomic-embed-text` loaded and the next 9B call pays a 4.8 s reload (0.8 s warm); the embed itself pays 2.2 s cold.
   `OLLAMA_MAX_LOADED_MODELS=1` is set in the user's environment. Every turn that embeds (saving a fact, recalling
   memory for a question of five words or more, the heartbeat's checks) therefore swaps models twice: that is why a
   `remember` turn takes 25 s and why the local median is 8.5 s. Options, in order: set
   `OLLAMA_MAX_LOADED_MODELS=2` and restart Ollama (9B 5.7 GB + nomic 0.3 GB fit in 8 GB; check `ollama ps` and the
   tok/s afterwards, since a context spill to CPU would be worse); or embed on the CPU in-process (fastembed, the same
   nomic model, about 0.1 s) and never touch the GPU for memory. Expected gain: 5 to 10 s off most local turns.
   **Done 2026-11-18 09:00:** `OLLAMA_MAX_LOADED_MODELS=2` set (user environment) and Ollama restarted. Both models
   resident, both 100 percent GPU, 7.0 of 8 GB used; an embed now takes 0.01 s warm and the next 9B call 0.25 s with no
   reload. Live `remember` turn 8.6 s (median before: 21.0 s over 32 turns), recall 9.4 s (22.2 s before). The old
   setting was also flaky: the Ollama log shows the embedder load failing with a CUDA "device busy" error while the 9B
   was still releasing VRAM (a 13.7 s HTTP 500 on `/api/embed`, 08:57 today, and the same crash on 2026-11-17 18:56).
2. **Two generations per tool turn.** The local decider and the local speaker are separate 9B passes, each with a
   long prompt (schemas, notes, history). Keeping the fixed parts of the prompt first and the changing parts last lets
   Ollama reuse the prompt cache between them. Worth measuring before changing. *Backend.*
3. **UI: the detail panel re-renders every 400 ms.** Each `vitals` frame (1 Hz) calls `scheduleDetail()`, which
   rebuilds the whole panel's `innerHTML` while it is open, including the rules and files lists. Patch the numbers in
   place and re-render on real changes only. Phones feel this. *UI.*
4. **UI load.** The shader library (1.2 MB) and HDR (1.5 MB) load only on the wide dashboard pages; `app.js` 115 KB
   and `app.css` 137 KB uncompressed are fine for Pages with gzip. The service worker is network-first with a cache
   fallback: good, as long as `VERSION` is bumped per deploy (it is, v51).
5. **Startup.** The embedding warm-up and the 120 s routine grace keep the first chats fast; `/health` reports
   `ready`. Good.

## 5. Code quality and efficiency, backend

1. **Every tool is declared in four places**: the registry dict in `tools.py`, the hand-written schema list in
   `Toolbox.schemas()`, `CORE_RISK` / `GUEST_TOOLS`, and `CORE_BAND` in the bridge. Adding the job tools tonight
   took five edits in three files. The integrations already use one `ToolSpec` per tool; the core tools should too
   (name, description, parameters, risk, guest flag, band in one row), with the schema list generated from it.
2. **Long functions.** `agent.py` is 1,387 lines and `_chat` about 300 with nested routing branches; `bridge.py` is
   1,206. Both work and are commented, but a change in one branch is hard to test in isolation (see 3.2). Splitting
   `_chat` into route → act → speak → check functions would help more than splitting files.
3. **Cue regexes.** About twenty cue patterns decide which tools are offered and which code paths run. They are
   testable (the suites cover them) but brittle; S1 `understand()` is the safety net. Fine for now.
4. **Error handling.** Broad `except Exception` with `# noqa: BLE001` and silent `pass` in persistence helpers.
   Nothing crashes, but some failures leave no trace. A `logging` logger with a rotating file in `data/logs/` and
   `log.exception` in those handlers would make the next bug like the email one visible without a transcript.
5. **Persistence.** Many small JSON files written whole with tmp + replace: robust and simple. `Bus._save()` writes
   `events.json` on every publish under the lock; fine at this volume.
6. **Tests.** 401 unit checks, 127 always-on checks, 134 hybrid checks, 55 live bridge checks, 67 eval cases, all
   passing tonight. Tests wrote to `data/logs/jobs.log` once (fixed: jobs log beside their own temp file).
7. **Config and secrets.** `config.json` plus Credential Manager, no secrets in the repo or logs. Good.
